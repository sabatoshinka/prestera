# Защита Pibble Club 0.2.0

## Подключение к комнате

Хозяин создаёт случайный секрет длиной 32 байта через `crypto.randomBytes`.
Он включён в приглашение и используется как предварительно переданный ключ
(PSK) для взаимной аутентификации в TLS. Не заменяйте его паролем или PIN-кодом:
защита рассчитана на случайный 256-битный секрет.

При каждом подключении к хозяину:

1. TLS выполняет новый обмен временными ключами **X25519 (ECDHE)**.
2. Обе стороны подтверждают владение секретом приглашения в TLS handshake.
   Сам секрет не передаётся. Подмена обмена стороной без секрета приводит
   к отказу в соединении.
3. TLS выводит сеансовые ключи для обоих направлений и защищает сообщения
   **ChaCha20-Poly1305**: шифрует содержимое и проверяет целостность.
4. Только после успешного TLS handshake возможны WebSocket upgrade и вход
   в комнату. До сообщения `hello` клиент не появляется в списке участников.

У разных подключений разные сеансовые ключи. Восстановление сессий через
идентификаторы или билеты отключено; переподключение требует нового ECDHE.
Закрытые временные ключи обрабатывает криптобиблиотека, приложение не сохраняет
их на диск. Позднее получение одного секрета приглашения само по себе не
позволяет расшифровать ранее записанные завершённые сеансы (forward secrecy).
Это не защищает от доступа к памяти работающего приложения или заражённого ПК.

### Конкретный протокол

`WSS → TLS 1.2 → TLS_ECDHE_PSK_WITH_CHACHA20_POLY1305_SHA256`, группа `X25519`.
Реализация — Node TLS и BoringSSL, включённые в Electron. Собственных реализаций
Diffie–Hellman, формирования nonce, тегов или расписания ключей нет.

Версия TLS и набор шифров зафиксированы с обеих сторон. CBC, обычный PSK без
ECDHE, другие кривые, TLS renegotiation и открытый `ws://` не разрешены.
Клиент дополнительно проверяет фактически согласованные протокол, шифр,
X25519, результат аутентификации и отсутствие восстановления сессии.

Причина выбора TLS 1.2: в используемом Electron 43.7.0 мост Node/BoringSSL
предоставляет `pskCallback` для внешних PSK в TLS 1.2. Пробное подключение с
TLS 1.3 через этот API не работает. Для TLS 1.3 BoringSSL использует отдельный
API credentials, которого нет в этом Node-мосте. Это не автоматический откат:
приложение допускает ровно один описанный набор. При обновлении Electron
совместимость необходимо повторно проверять через `npm run test:electron`.

Сертификаты и внешние центры сертификации не нужны: аутентификацию выполняет
PSK. `rejectUnauthorized` остаётся включён; проверка имени сертификата заменена
в контексте строго единственного PSK-набора, где сертификат не используется.

## Голос, видео, чат и файлы

Участники создают прямые попарные WebRTC-соединения. Медиадорожки защищены
DTLS-SRTP, RTCDataChannel для чата и вложений — SCTP поверх DTLS.
SDP и отпечатки сертификатов WebRTC передаются через защищённую связь с хозяином.
Хозяин управляет составом комнаты и пересылает служебные сообщения; он является
доверенной стороной. Независимой проверки личности по ключам или кодам сверки нет.
Дополнительное оборачивание видеокадров в своё шифрование не применяется.

## Доступ и ограничения

- Сканер может обнаружить порт, но без секрета не проходит TLS-аутентификацию.
- Приглашение — пропуск в комнату. Любой получивший его может войти; все
  владельцы секрета относятся к доверенной группе. Общий PSK не различает хозяина
  и остальных владельцев секрета при криптографической аутентификации.
- Ники не удостоверяют личность. Ручного одобрения входа, отдельных ключей
  участников, блокировки конкретного человека и отзыва одной ссылки нет.
- При утечке приглашения нужно закрыть комнату и создать новую. У новой комнаты
  другой секрет, старые приглашения не подходят.
- Для комнаты максимум 8 участников; TCP-соединений максимум 24. С одного IP
  допускаются до 12 одновременных соединений и 30 новых попыток за 10 секунд.
  Незавершённое подключение ограничено тайм-аутами, список адресов ограничен
  1024 записями и очищается. Для WebSocket ограничены частота и размер сообщений.
  Это ограничивает расход ресурсов, но не является защитой от DDoS. Несколько
  друзей за одним NAT делят лимит IP.
- Встроенный UDP STUN отвечает без аутентификации на ограниченные запросы
  определения адреса. Он не передаёт сообщения, ключи или медиаданные.
- P2P не скрывает IP участников. Сетевой наблюдатель видит адреса, время и объём
  трафика. Любой участник может записать доступные ему звук, экран и сообщения.
- История, настройки и вложения в `PibbleData` не имеют отдельного шифрования
  приложением. Безопасность локальных данных зависит от доступа к Windows и диску.
- Профессиональный аудит и независимый пентест не проводились. Пройденные
  автоматические сценарии описаны в `VALIDATION.md`.
